# Meerya Windows Duplex Audio Thread Summary

Date range: 2026-07-01 through 2026-07-08  
Repo: `Syzygyx/meerya-esp32`  
Primary objective: make Meerya work as a reliable full-duplex USB speakerphone on Windows, especially Windows 10/11 browser and native audio paths.

## Executive Summary

This week was a concentrated push on Meerya's ESP32-S3 USB audio firmware, web installer, and Windows validation loop. The work moved from basic USB enumeration and static/garbled audio debugging into a UAC1 Windows profile, web-flasher deployment, native Windows WASAPI tests, Chrome/WebRTC probes, Google Meet investigation, and finally deep TinyUSB/UAC panic instrumentation.

The most important positive result was a native Windows WASAPI full-duplex soak that passed for nearly five minutes on firmware identity `0259`, recorded in `reports/windows-duplex/win-0259-duplex-5min.json`. That run captured 294.98 s of microphone audio while rendering 300.55 s of speaker output, with firmware speaker and microphone counters advancing and no USB transport errors, queue drops, short writes, or clipping. Chrome/WebRTC microphone capture also passed, including Meet-origin probes and a mixed Chrome microphone plus native speaker output test.

The most important unresolved issue is that later firmware attempts regressed into a Windows native duplex failure where capture stops after about 0.2-0.28 s, playback stops after about 1.5 s, firmware stream counters do not advance, and the ESP32 reports reset reason `PANIC`. The latest durable breadcrumbs show the crash path happens around a standard USB `SET_INTERFACE` request (`bRequest=11`) for UAC1 microphone streaming interface `2`, alternate setting `0`, before speaker or microphone alt-setting counters advance. Commit `a5ba54e` removed one suspicious TinyUSB FIFO clear from that idle-alt path, but this turn was interrupted before rebuilding, OTA loading, and retesting that exact commit.

## Major Decisions

### Use UAC1 For Windows

The thread converged on UAC1 for Windows compatibility. UAC2 was kept in the codebase for macOS-style profiles, but the Windows descriptor path uses UAC1 at 48 kHz mono.

Reasons:

- Windows was not behaving reliably with the earlier UAC2/feedback configuration.
- A reference USB audio descriptor showed a UAC-style adaptive OUT endpoint without a separate feedback endpoint.
- UAC1 is simpler and broadly supported by Windows class drivers.

Tradeoffs noted:

- UAC1 is older and less expressive than UAC2.
- It is usually limited to simpler sample format/rate/control models.
- For this product, 48 kHz mono in/out is sufficient, so those disadvantages were acceptable.

### Prioritize Microphone Over Speaker, Video Last

The working product requirement was full-duplex speakerphone behavior, but microphone correctness was prioritized over speaker polish, and UVC camera support was moved to the bottom of the realtime priority list. UVC was backed out/disabled from the Windows focus path when it complicated audio validation.

### Default To Web-Installable Firmware

A recurring product requirement was that customers should be able to flash from a public GitHub Pages web installer. The source repo was updated so pushes to `meerya-esp32` can refresh the separate public installer repo, `meerya-esp32-installer`, via GitHub Actions and deploy tooling.

Important files:

- `.github/workflows/deploy-installer.yml`
- `scripts/update-web-installer-firmware.py`
- `scripts/deploy-web-installer.py`
- `docs/installer/index.html`
- `docs/installer/firmware/manifest.json`

### Keep Windows Profile Switchable

The firmware supports saving a host profile in NVS and rebooting to switch descriptor sets. This matters because macOS and Windows prefer different USB audio behavior, especially around feedback/adaptive speaker OUT handling.

### Latest Narrow Patch

Commit: `a5ba54e` Avoid clearing UAC IN FIFO on idle alt.

Reason:

- `set_mic_idle` called `tud_audio_n_clear_ep_in_ff(MEERYA_UAC_MIC_FUNC_ID)`.
- TinyUSB already clears FIFOs when it actually closes an active endpoint.
- In the zero-endpoint alternate setting path, manually clearing the IN FIFO from the app callback may be unsafe or redundant.

Status:

- The patch was committed and pushed.
- The previous work turn was interrupted before rebuilding exact commit metadata, OTA loading `a5ba54e`, and rerunning the Windows duplex test.

## Mac / Linux / VM Findings

Mac was useful for build, OTA, and some local audio sanity checks. The PWA speakerphone test and triggered tones could sound clean on Mac, which helped distinguish firmware audio path issues from Windows/VM transport issues.

Parallels and VM-based Windows/Linux testing were unreliable for USB audio timing. The thread moved toward native Windows on WinBook because VM timing and USB pass-through could obscure real UAC behavior.

Debian and Parallels were used during the investigation, but native Windows became the authoritative target for customer compatibility.

## Audio Quality Findings

Problems observed:

- Static/garbled speaker output.
- Static/garbled microphone recordings.
- Clicking from speaker.
- Crackly tone on macOS at some points.
- Voice sounded garbled in some builds.
- Microphone recording had occasional pops.
- Web output test sometimes reported clipping.

Mitigations attempted:

- Switched to UAC1 Windows descriptor.
- Tried 48 kHz mono.
- Prioritized microphone path.
- Adjusted mic packet sizes and service intervals.
- Tried 1 ms, 2 ms, 5 ms, 10 ms, and batched Windows UAC1 mic packet strategies.
- Added USB mic diagnostic tone.
- Added timing and packet counters.
- Increased speaker queue margin.
- Changed test tones to softer chimes to make repeated tests less unpleasant.
- Added speech WAV stimulus to installer.
- Smoothed microphone capture pops.

Current quality state:

- There is proof that a previous Windows native duplex build could run long enough for a five-minute soak.
- Later builds are failing before audio counters advance, so current audio quality cannot be evaluated until the panic/regression is resolved.
